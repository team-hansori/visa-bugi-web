- 대상: `2026_ICT융합공모전_비자부기_사업계획서_최종안.docx`
- 관련 PR: [#30](https://github.com/team-hansori/visa-bugi-web/pull/30)
- 검토 기준일: 2026-08-28
- 목적: 표현 교정보다 심사 관점의 논리, 증거, 사업성, 구현 신뢰도를 우선 점검한다.

## 1. 총평

현재 계획서는 **복잡한 체류·비자 정보를 구조화하는 기술과 데이터 설계 역량**은 잘 보여준다. 반면 사업계획서가 반드시 답해야 할 두 질문, 즉 **“누가 지금 반드시 써야 하는가”와 “누가 왜 비용을 지불하는가”**에 대한 답은 약하다.

지금 상태로 제출하면 기술기획서로는 좋은 평가를 받을 수 있지만, 사업성 심사에서는 다음과 같은 인상을 줄 가능성이 크다.

> 기능과 사회적 의미는 많지만, 첫 고객·구매자·검증 근거·매출 전환 경로가 선명하지 않다.

가장 먼저 해야 할 일은 기능을 더 추가하는 것이 아니라, **첫 고객과 첫 문제를 하나로 좁히고 그 문제를 실제 근거로 증명하는 것**이다.

## 2. 핵심 주장 재정의

### 권장 한 문장

> 비자부기는 충북 소재 대학 국제교류부서가 외국인 유학생의 F-2-R 전환 상담을 표준화하고, 학생이 준비 서류 누락 없이 신청 절차를 완료하도록 돕는 근거 기반 업무지원 서비스다.

이 문장은 다음을 분리한다.

- 사용자는 외국인 유학생이다.
- 초기 구매자는 충북 소재 대학의 국제교류부서다.
- 첫 번째 과업은 F-2-R 전환 상담과 신청 준비다.
- 핵심 가치는 상담 표준화, 탐색시간 단축, 서류 누락 방지다.
- 차별점은 생성형 답변 자체가 아니라 출처·시점·조건을 추적할 수 있는 구조화된 규칙 데이터다.

대학을 첫 구매자로 확정하기 어렵다면 지자체·기업 등 다른 구매자를 택할 수 있다. 다만 제출본에서는 **하나의 초기 구매자만 전면에 두고**, 나머지는 확장시장으로 내려야 한다.

## 3. 우선순위별 핵심 문제

| 우선순위 | 문제 | 심사상 위험 | 수정 방향 |
|---|---|---|---|
| P0 | 고객과 구매자가 너무 많음 | 유학생, 근로자, 기업, 대학, 지자체의 문제가 달라 누구를 위한 서비스인지 흐려짐 | 초기 사용자 1개, 초기 구매자 1개, 핵심 과업 1개로 고정 |
| P0 | 수요 증거가 부족함 | 거주 외국인 수와 유학생 수는 시장 배경일 뿐, 비자부기 사용 의향이나 지불 의사를 증명하지 못함 | 학생·담당자 인터뷰와 현재 업무시간·누락·반복문의 기준값 제시 |
| P0 | 구현 상태가 실제 저장소보다 앞서 보임 | 한 번의 과장이 데이터·성과·로드맵 전체의 신뢰도를 훼손할 수 있음 | 모든 기능을 구현·데모·UI 시안·설계 완료·구현 예정으로 명시 |
| P1 | MVP 범위가 지나치게 넓음 | 온보딩, 규칙 판정, 서류, 캘린더, 지도, OCR, 번역, 챗봇, 위험상황 연계를 동시에 검증하기 어려움 | F-2-R 한 경로의 조건 확인→서류 준비→일정 관리만 1차 MVP로 제한 |
| P1 | 경쟁 대상을 잘못 잡음 | 포털·범용 AI·캘린더만 비교하면 사용자가 실제로 택하는 대안을 놓침 | 대학 국제처, 행정사, 지원센터, HiKorea·1345, 커뮤니티, 기업 HR과 비교 |
| P1 | 사업모델이 방향 수준임 | “B2C 무료, B2B/B2G 유료”만으로는 구매 예산과 계약 가능성을 판단할 수 없음 | 구매부서, 파일럿 방식, 가격 단위, ROI, 유료 전환 조건을 명시 |
| P1 | 데이터 구축량이 성과처럼 제시됨 | 테이블·행·테스트 수는 산출물이지 고객가치나 정확성의 증거가 아님 | 출처 연결률, 갱신 리드타임, 오류율, 검수율, 미해결 충돌 건수로 전환 |
| P1 | 기대효과의 인과가 멂 | 지역 정착·인력난 해소·정책 개선은 단기간에 비자부기가 직접 만들기 어려움 | 탐색시간, 누락률, 상담 준비도, 반복문의, 공고 반영시간을 1차 KPI로 설정 |
| P2 | 운영 거버넌스가 없음 | 규칙형 서비스는 일관되게 틀린 답을 낼 위험이 있으며 책임주체가 불명확함 | 수집→구조화→도메인 검수→배포→변경 알림의 담당자와 SLA 명시 |
| P2 | 민감정보 처리 원칙이 부족함 | OCR과 서류 업로드는 개인정보·여권·체류정보 처리 위험을 키움 | 임시처리, 저장 여부, 삭제주기, 마스킹, 동의, 위탁처리 범위를 정의 |

## 4. 고객과 문제: “대상 인구”가 아니라 “지금의 고통”을 증명해야 함

현재 인구·유학생 통계는 “시장이 존재한다”는 배경으로는 유효하지만, 아래 질문에는 답하지 못한다.

- 사용자가 비자 정보를 찾는 데 실제로 얼마나 걸리는가?
- 대학 담당자는 같은 질문에 월 몇 번 답하는가?
- 신청 서류 누락이나 기한 착오가 얼마나 발생하는가?
- 현재 어떤 도구와 사람을 조합해 문제를 해결하는가?
- 그 불편을 줄이기 위해 누가 예산을 쓸 의향이 있는가?

### 제출 전 최소 증거

| 검증 대상 | 최소 확보 자료 | 계획서에 넣을 결과 |
|---|---|---|
| 외국인 유학생 문제 | F-2-R 전환 관심 학생 5~10명 인터뷰 | 상위 3개 어려움, 현재 해결법, 평균 탐색시간 |
| 대학 담당자 문제 | 충북 대학 국제처 담당자 3곳 이상 인터뷰 | 반복문의 빈도, 1건당 대응시간, 오류·누락 유형 |
| 구매 가능성 | 부서장 또는 예산 관여자 2곳 이상 확인 | 파일럿 참여 조건, 예산 항목, 의사결정 절차 |
| 제품 효용 | 실제 공고와 신청 시나리오 기반 사용성 테스트 | 완료율, 소요시간, 누락률, 만족도 |

인터뷰 전이라면 페르소나를 실제 사용자처럼 단정하지 말고 **“가설 페르소나”**로 표시해야 한다. 인터뷰 수치가 없다면 임의로 만들지 말고 “파일럿에서 측정할 기준값”으로 남기는 편이 낫다.

## 5. MVP: 한 비자, 한 사용자, 한 종단 흐름

현재 기획의 기능을 모두 MVP로 제시하면 개발 가능성보다 욕심이 먼저 보인다. 1차 범위는 다음 세 단계면 충분하다.

1. 사용자가 현재 조건을 입력하고 F-2-R 검토에 필요한 조건과 미충족 항목을 확인한다.
2. 각 조건의 출처·기준일·예외와 준비서류 체크리스트를 확인한다.
3. 마감일과 다음 행동을 저장하고 변경 공지를 받는다.

### 1차 범위에 남길 것

- F-2-R 조건 구조화와 AND/OR 판정
- 조건별 근거 출처와 기준일 표시
- 개인별 미충족 조건·준비서류 체크리스트
- 핵심 일정 저장과 변경 알림
- 대학 담당자가 같은 기준으로 상담할 수 있는 요약 화면

### 후속 단계로 내릴 것

- 범용 OCR 자동 인식과 자동 마스킹
- 자유대화형 챗봇과 RAG
- 폭력·노동피해 등 위험상황 분류·연계
- 전국 비자 유형 확대
- 다기관 통합 대시보드
- 고도화된 다국어 자동번역

특히 위험상황 연계는 사회적 의미는 크지만 법률·안전·오분류 책임이 추가된다. 초기 사업의 핵심이 아니라면 공식기관 연결 링크 수준으로 제한하고 상세 기능은 후속 로드맵이나 부록으로 보내는 편이 안전하다.

## 6. 구현 신뢰도: 반드시 사실대로 층위를 나눌 것

2026-08-28 현재 PR 브랜치의 저장소를 기준으로 보면, 최종안에서 현재 기능처럼 읽힐 수 있는 일부 항목은 실제로는 데모 또는 계획 단계다.

| 항목 | 저장소에서 확인되는 상태 | 계획서 권장 표현 |
|---|---|---|
| 출처·규칙 데이터 구조 | 데이터·스키마·검증 자산 존재 | 구현 완료. 단, 범위·정확도·갱신 지표는 별도 검증 필요 |
| 규칙 판정 엔진 | 기존 설계 문서상 미구현 | 구현 예정 또는 설계 완료 |
| 캘린더 | `DemoCalendar` 사용 | 데모 구현 |
| 기관 지도 | `AgencyMapDemo` 사용 | 데모 구현 |
| OCR | 업로드 UI에 “OCR 분석과 자동 마스킹은 아직 연결되지 않았습니다”라고 명시 | UI 프로토타입, 연동 예정 |
| API | 현재 `app/api/health/route.ts` 중심 | 헬스체크 구현, 서비스 API 구현 예정 |
| 다국어 | 여러 locale 파일이 한국어 폴백을 포함 | 번역 구조 구현, 콘텐츠 번역·검수 진행 예정 |
| 챗봇·RAG·벡터DB | 기존 설계 문서상 미구현 | 후속 구현 예정 |

계획서에는 아래 범례를 명시하고 기능마다 하나를 붙이는 것이 좋다.

- **구현 완료**: 실제 입력·처리·출력과 테스트가 연결됨
- **데모 구현**: 고정·샘플 데이터로 사용 흐름을 확인할 수 있음
- **UI 프로토타입**: 화면만 존재하며 핵심 처리 로직은 연결되지 않음
- **설계 완료**: 데이터 구조나 상세 명세만 존재함
- **구현 예정**: 일정과 책임자만 정의됨

기술을 적게 보이게 하는 것보다 **구현 경계를 정확히 밝히는 것이 심사 신뢰도에 훨씬 유리하다.**

## 7. 경쟁: 제품이 아니라 사용자의 현재 대안과 비교해야 함

실제 경쟁자는 비슷한 앱만이 아니다.

| 현재 대안 | 사용 이유 | 비자부기가 이겨야 할 지점 |
|---|---|---|
| 대학 국제교류부서 | 신뢰할 수 있고 학교 상황을 알고 있음 | 반복상담 감소, 동일 기준 안내, 사전 준비도 향상 |
| 행정사 | 복잡한 사례를 맡길 수 있음 | 일반 사례의 비용·시간 절감, 예외 사례는 전문기관으로 연결 |
| 외국인 지원센터·1345 | 공식 또는 준공식 상담 채널 | 대기 없이 개인 조건을 정리하고 출처와 다음 행동을 기록 |
| HiKorea·정부 공고 | 원문과 공식성 | 여러 문서의 조건·기한·서류를 한 흐름으로 구조화 |
| 온라인 커뮤니티·지인 | 빠르고 경험 기반임 | 최신성·출처·적용 범위를 검증할 수 있음 |
| 기업 HR | 취업·채용 맥락을 함께 처리함 | 담당자 수작업 감소와 후보자별 준비상태 가시화 |

경쟁표의 평가축도 “기능 유무”보다 다음처럼 바꾸는 것이 좋다.

- 답을 얻는 데 걸리는 시간
- 출처와 기준일 추적 가능 여부
- 개인 조건 판정 가능 여부
- 공고 변경 반영 속도
- 서류 누락 방지 수준
- 담당자 업무 절감 효과
- 예외 사례의 사람 검수·전문가 연결 가능 여부

## 8. 사업모델: 무료/유료가 아니라 구매 경로를 써야 함

권장 초기 경로는 다음과 같다.

> 충북 대학 1곳 무상 파일럿 → 상담시간·누락률 기준값과 개선치 측정 → 2~3개 대학 공동 실증 → 학기 또는 연 단위 운영 계약

계획서에는 최소한 아래 항목이 있어야 한다.

- 구매부서: 국제교류처, 산학협력단, 지자체 외국인정책 부서 중 누가 계약하는가?
- 구매 이유: 상담시간 절감, 민원 감소, 유학생 지원성과, 정착사업 실적 중 무엇인가?
- 가격 단위: 기관당 월·연 구독, 학생 수 구간, 파일럿 비용 중 무엇인가?
- 의사결정자: 실무자, 부서장, 예산 담당자 중 누가 승인하는가?
- 도입 장벽: 개인정보 검토, 공공조달, 법률책임, 기존 시스템 연동은 무엇인가?
- 유료 전환 조건: 어떤 KPI를 달성하면 다음 계약으로 넘어가는가?

### ROI를 보여주는 최소 공식

> 연간 절감가치 = 월 반복문의 건수 × 건당 절감시간 × 담당자 시간가치 × 12개월

여기에 서류 누락 감소, 공고 업데이트 시간 감소 등 측정 가능한 효과를 추가할 수 있다. 단, 실제 측정 전에는 예상값과 실측값을 구분해야 한다.

## 9. 데이터 자산: 규모보다 유지 가능한 품질이 중요함

13개 테이블, 1,101개 행, 684개 매핑, 407개 테스트와 같은 숫자는 개발 진척을 보여주지만 사업적 해자를 바로 증명하지는 않는다. 다음 운영지표로 전환해야 한다.

- 조건별 공식 출처 연결률
- 출처별 최종 확인일과 최신성
- 공고 변경 인지 후 서비스 반영까지의 시간
- 자동 검증 통과율과 사람 검수율
- 상충하는 규정·공고의 미해결 건수
- 테스트 사례 기준 판정 정확도와 오류율
- 비자 유형 1개를 추가·갱신하는 데 드는 시간과 비용

또한 **누가 어떤 주기로 검수하고, 충돌이 발생하면 누가 최종 승인하는지**가 있어야 한다. 권장 운영 흐름은 다음과 같다.

> 공식 공고 수집 → 원문 보존 → 구조화 → 자동 검증 → 도메인 검수 → 배포 승인 → 변경 이력 기록 → 영향 사용자 알림

“AI가 최신 정보를 제공한다”는 표현만으로는 부족하다. 데이터 갱신 SLA, 검수 책임자, 오류 신고·정정 절차를 함께 제시해야 한다.

## 10. KPI: 장기 사회성과와 단기 제품성과를 분리할 것

지역 정착률 향상, 인력난 완화, 정책 고도화는 장기 기대효과로 둘 수 있지만 초기 실증 KPI로 쓰기에는 인과관계가 너무 멀다.

### 1차 파일럿 KPI

- F-2-R 준비 과업 완료율
- 조건·서류 탐색에 걸린 중앙값 시간
- 신청 전 발견된 누락서류 수와 최종 누락률
- 학생의 상담 전 준비도
- 담당자의 반복설명 시간과 문의 건수
- 공고 변경 후 데이터 반영시간
- 출처가 표시된 답변 비율
- 잘못된 판정·정정 건수

### 장기 성과지표

- 비자 전환 신청·승인 과정의 중도 이탈 감소
- 대학의 외국인 유학생 지원성과 개선
- 충북 내 취업·정착 연계율
- 축적된 익명 통계의 정책 활용

두 층위를 섞지 말고 “제품이 직접 바꾸는 것”과 “장기적으로 기여하는 것”을 분리해야 한다.

## 11. AI·개인정보·책임 범위

### AI 역할

현재 강점은 LLM 자체보다 **결정론적 규칙 구조와 근거 추적성**에 가깝다. 따라서 “AI 혁신”을 전면에 세우기보다 AI가 정확히 무엇을 하고 무엇을 하지 않는지 밝히는 편이 설득력 있다.

- 규칙 엔진: 명시적 조건 판정과 누락 항목 계산
- AI 보조: 원문 요약, 질의 의도 분류, 번역 초안 등
- 사람 검수: 예외·충돌·고위험 답변 승인
- 금지 범위: 법률대리 또는 승인 가능성 보장

### 민감정보 처리

OCR과 서류 업로드를 제시하려면 다음 원칙을 최소한 명시해야 한다.

- 원본 문서의 서버 저장 여부와 보관기간
- 분석 후 즉시 삭제 또는 사용자 선택 삭제
- 여권번호·외국인등록번호 등 자동 마스킹 범위
- 외부 OCR·AI 사업자 사용 여부와 처리 위치
- 사용자 동의와 처리 목적
- 접근 로그, 유출 대응, 오류 신고 절차

이 원칙을 설계하지 못했다면 OCR은 1차 MVP에서 제외하는 편이 낫다.

## 12. 충북 특화성을 더 강하게 증명할 것

“충북에서 시작한다”와 “충북이기 때문에 이 서비스가 필요하다”는 다르다. 아래 중 실제 근거가 있는 요소를 본문에 넣어야 한다.

- 충북의 지역특화형 비자 공고와 변경 구조
- 지역 대학 국제처가 겪는 반복상담·인력 제약
- 충북 소재 기업의 외국인 인재 채용 경로
- 지역 지원기관·대학·기업과의 파일럿 가능성
- 전국 공통 서비스가 놓치는 충북 기관·기한·요건 데이터

협력기관이 확정되지 않았다면 로고나 “협력” 표현을 사용하지 말고, 접촉·제안·논의·확정 단계를 구분해야 한다.

## 13. 팀 역량과 실행 책임

최종안에는 기능만큼 다음 역할의 소유자가 보여야 한다.

- 비자·행정 데이터 수집 및 갱신 책임자
- 도메인 검수자 또는 자문 네트워크
- 제품·프론트엔드·백엔드 구현 책임자
- 사용자 조사와 대학 파일럿 운영 책임자
- 개인정보·보안 대응 책임자

팀 내부에 도메인 전문가가 없다면 숨기지 말고, 행정사·대학 담당자·지원센터 실무자와 어떤 방식으로 검수 체계를 만들 것인지 제시해야 한다.

## 14. 본문에서 줄이고 추가할 내용

### 줄일 내용

- 유사한 두 개의 사용자 여정 중 하나
- 위험상황 연계의 세부 기능
- AND/OR 규칙과 출처 추적 구조의 반복 설명
- 심사자가 고객가치와 연결하기 어려운 기술스택 나열
- 구현되지 않은 미래 기능과 전국 확장 서술

### 추가할 내용

- 실제 사용자·담당자 인터뷰 결과
- 첫 구매자와 구매 절차
- 정직한 구현 상태표
- 파일럿 확보 경로와 전환 조건
- 업무시간·누락률 기반 ROI
- 데이터 갱신·검수 운영체계
- 접근 가능한 시장(SAM)과 초기 목표시장(SOM)
- 팀 역할과 도메인 검수자

기술 설명을 20~30% 줄여 확보한 지면을 고객증거, 구매경로, 실증 KPI, 팀 실행력에 배분하는 것을 권장한다.

## 15. 심사 관점의 현재 점수 추정

아래 수치는 공식 평가가 아니라 현재 문서를 기준으로 한 주관적 진단이다.

| 항목 | 현재 추정 | 핵심 이유 |
|---|---:|---|
| 문제 중요성 | 8/10 | 외국인의 복잡한 체류·비자 정보 접근 문제는 명확함 |
| 기술·데이터 설계 | 9/10 | 출처·규칙·검증 구조가 구체적임 |
| 차별성 | 7/10 | 근거 추적형 구조는 유효하나 대체재 대비 검증이 부족함 |
| 구현 신뢰도 | 4/10 | 문서 표현과 실제 구현 단계의 경계가 흐림 |
| 고객 검증 | 2/10 | 인터뷰·사용성 테스트·수요 증거가 거의 없음 |
| 사업모델 | 3/10 | 구매자·가격·ROI·계약경로가 불명확함 |
| 시장 진입 | 3/10 | 첫 기관 확보와 유료 전환 계획이 부족함 |

합격 가능성을 가장 크게 높일 수정은 기술기능 추가가 아니라 **고객 검증, 구현 경계 정정, 첫 구매자 명시**다.

## 16. 제출 전 차단 항목

내용 수정과 별도로 다음은 최종 제출 전에 반드시 확인해야 한다.

- 기존 설계 문서의 15쪽 제한과 최종 제출 파일의 실제 페이지 수를 동일한 환경에서 재확인한다.
- 사용 글꼴이 제출 환경에서 대체될 때 줄바꿈과 페이지 수가 달라지지 않는지 PDF로 검증한다.
- 사용자 여정의 단계 번호가 두 번째 여정에서 6~10으로 이어지는 문제와 사업모델의 11~13 번호를 문맥에 맞게 다시 시작한다.
- 화면 이미지가 작거나 한쪽으로 치우친 페이지는 실제 구현·데모·UI 프로토타입을 구분한 캡션과 함께 재배치한다.
- 파일명, 버전, 제출일, 팀명, 연락처와 외부 링크의 유효성을 마지막으로 확인한다.

## 17. 최종 수정 순서

1. 최종안의 모든 기능을 구현·데모·UI·설계·예정으로 다시 분류한다.
2. 첫 사용자, 첫 구매자, 첫 비자 과업을 하나씩 확정한다.
3. 학생·대학 담당자 인터뷰로 문제의 기준값을 확보한다.
4. MVP에서 OCR·챗봇·위험상황 등 주변 기능을 분리한다.
5. 경쟁표를 실제 대안 중심으로 다시 작성한다.
6. 파일럿→효과 측정→유료 계약의 경로와 ROI를 제시한다.
7. 산출물 개수 대신 데이터 품질·갱신·검수 지표를 넣는다.
8. 단기 제품 KPI와 장기 사회성과를 분리한다.
9. 팀 역할, 도메인 검수, 개인정보 처리 원칙을 보강한다.
10. PDF 기준 페이지 수·번호·폰트·캡션을 최종 검수한다.
